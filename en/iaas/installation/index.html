Installation with OneDeploy

Assignment

"The board chose OpenNebula," Simone Wyss writes. "The software is free, it comes from Europe and it runs on our three servers. Can you install it in a way we can repeat any time we add a server? And please write down what runs where afterwards, so we still know a year from now."

Learning goals

After this chapter you can:

  • Explain how Ansible works with inventories, playbooks, tasks, modules, roles and handlers
  • Run a small playbook of your own and recognize idempotence in its output
  • Describe how OneDeploy is organized
  • Install OpenNebula 7.4 with one run of OneDeploy
  • Name the services that run on the front-end and the nodes afterwards and how they work together
  • Read the message of a run that stopped and fix the problem

Ansible

Section titled “Ansible”

You could set up a cloud of three servers by hand. With thirty servers, or with a server that has to be rebuilt after a failure, that becomes slow and error-prone. Configuration management tools therefore describe the desired state of the servers in files and bring the servers into that state. Ansible is one of them, and it is the tool the OpenNebula project uses to automate its installations.

Ansible needs no agent. The target machines only need SSH and Python. Ansible runs on a control machine, in your lab the front-end. From there it connects to the targets, copies small programs over, runs them and deletes them again. This is called a push model because the control machine initiates the changes.

Ansible describes target states. A shell script says "install package X". An Ansible task says "package X is installed". If that is already true, Ansible does nothing and reports ok. If it has to change something, it reports changed. This property is called idempotence. You can repeat a run as often as you like and get the same result.

OneDeploy

Section titled “OneDeploy”

OneDeploy is an Ansible collection by the OpenNebula project. It installs a cloud from a front-end and several nodes, optionally with high availability, Ceph storage or a routed network. The course is tested with the version release-1.4.1 and uses only its simplest layout with local storage.

The playbook opennebula.deploy.main has two parts. The part pre prepares all machines. It checks Python and the machine names, distributes SSH keys and sets up time synchronization and logging. The part site then installs OpenNebula. It consists of plays for the groups of the inventory:

  1. All machines with the role common, shared packages and the OpenNebula package source
  2. The front-end with the roles database, opennebula/server, gate, flow, form and gui
  3. The nodes with the roles kvm, datastore/node and network/node
  4. The front-end once more with datastore/frontend and network/frontend, which create the datastores and networks and register the nodes as hosts

Roles for features the inventory does not turn on, such as Ceph, a routed network or Prometheus, are skipped. They show up as skipping in the output.

Setting up OneDeploy

Section titled “Setting up OneDeploy”

The script lab/one-deploy/install.sh installs Ansible from the Ubuntu packages, fetches OneDeploy at the course version into ~/cc-lab/one-deploy and installs the Ansible collections OneDeploy needs. The guide Using the Playbooks in the OneDeploy wiki shows the same steps one by one.

While it installs the collections, Git reports a "detached HEAD" state. OneDeploy requires one collection at a fixed version, so Git checks out a tag instead of a branch. The message is not an error. The script has succeeded when it ends with the line one-deploy release-1.4.1 is ready.

The inventory

Section titled “The inventory”

The inventory describes your lab for OneDeploy. The script make-inventory.sh writes it from your personal parameters, and on its first run it creates a random password for the user oneadmin, the administrator of OpenNebula. The password then lives in ~/cc-lab/oneadmin.pass.

The group frontend holds the front-end, the group node the two nodes. Since Ansible runs on the front-end, it connects to it locally instead of over SSH, as ansible_connection: local specifies. Values under vars apply to all machines. one_version sets the version of OpenNebula, and ds with mode: ssh means the nodes receive images over SSH, so no shared storage is needed. You create the networks for your members' VMs yourself in chapter 2.3, which is why the inventory has none yet. For groups, variables and connection types in an inventory, see the inventory guide of ansible-core 2.20.

Before you install, check that Ansible reaches all three VMs.

Every VM answers with SUCCESS and ping: pong. Before that, Ansible warns for each VM that it discovered the Python interpreter on its own. You can ignore this warning.

A first playbook

Section titled “A first playbook”

The course's example puts a greeting with the name of the cooperative on every node. It installs a package, writes a file with facts about the node and then has a handler read the file with cat.

Run it twice. In the first run at least the task with the greeting reports changed, and the handler runs. If htop is already installed, as on smartlearn, the task for the package reports ok. You see the greeting itself at your next login on a node or with cat /etc/motd. Ansible only prints what cat returns in the handler when you start ansible-playbook with the option -v. The second run reports ok everywhere and changed=0. This time the handler does not run, because nothing changed. The line gather_facts: true is needed because OneDeploy turns off the automatic gathering of facts in its configuration. The introduction to playbooks of ansible-core 2.20 covers their structure, how they run and idempotence.

Installing OpenNebula

Section titled “Installing OpenNebula”

A run of OneDeploy takes a few minutes, between one and a half and three in the course lab and about four on smartlearn. On a slow network it takes much longer. Ansible shows every role and every task with its result per machine. OpenNebula 7.4 describes the same workflow with a control node, an inventory and playbooks in its OneDeploy guide.

The output ends with the section PLAY RECAP and one line per VM. After a successful installation every line shows failed=0 and unreachable=0. ok counts every task that ran without an error, including the ones that changed something. changed counts only the tasks among them that made a change, and skipped the tasks your lab did not need. On smartlearn a run showed ok=119 changed=34 failed=0 for the front-end and ok=78 changed=16 failed=0 for each node. If failed or unreachable shows a number above 0, the section Reading a run that stopped shows how to find the cause.

The installed services

Section titled “The installed services”

After the run, OpenNebula is fully installed. The details below come from a lab of the course with OpenNebula 7.4.1 on Ubuntu 26.04.

On top of that come the user oneadmin with an SSH key pair, time synchronization with chrony and the configuration under /etc/one/, mainly oned.conf. Inside OpenNebula the run creates three datastores. The datastore system with ID 0 holds the disks of running VMs, default with ID 1 the images, and files with ID 2 files such as kernels or context scripts. All three use the transfer driver ssh.

Front-end and nodes working together

Section titled “Front-end and nodes working together”

When you start a VM, oned records it in the database, and the scheduler picks a node with enough free CPU and memory. The front-end then connects to that node as oneadmin over SSH. The transfer driver ssh copies the VM's image into the node's system datastore under /var/lib/one/datastores/0/. Then a driver on the node starts the VM through libvirt with KVM. The drivers are small Ruby and shell programs that the front-end copies to /var/tmp/one/ on every node. That is what the handler "Sync Remotes" does at the end of a run. From then on onemonitord regularly queries the state of nodes and VMs, which oned shows in onehost list and the web interface.

Reading a run that stopped

Section titled “Reading a run that stopped”

When a run stops, a line further up starts with fatal: and the name of the VM, with the message below it. Above that, Ansible shows the task that failed and the file it comes from. Read the message first, then the task. Most of the time the message already explains the problem.

While this course was being developed, the run stopped four times. Today the preparation script from chapter 0.4 prevents each of these stops:

MessageCauseHow the course handles it
Please make sure each cluster member can resolve all Front-end hostnamesThe VMs did not know each other's names.prepare.sh writes all names to /etc/hosts, and the inventory sets ensure_hosts.
Could not find the requested service rsyslog.serviceThe minimal Ubuntu 26.04 image does not include rsyslog.prepare.sh installs rsyslog on all VMs.
opennebula-fireedge ... Depends nodejs (<= 21)Ubuntu offers a newer Node.js than the web interface accepts.prepare.sh makes Node.js come from the OpenNebula repository.
Failed to set permissions on the temporary files Ansible needs to create when becoming an unprivileged userOn the front-end Ansible switches to the user oneadmin and needs the package acl for that.prepare.sh installs acl on the front-end.

After a fix, start the run again. Since Ansible describes the target state, it only changes what is not right yet.

The CLI as your user

Section titled “The CLI as your user”

The OpenNebula commands such as onehost or onevm log in to the API with the user and password from the file ~/.one/one_auth. So that you do not have to switch to oneadmin every time, you create this file for your own user with the password from the inventory. Only you may read it. The CLI configuration of OpenNebula 7.4 lists the other variables and files the CLI reads.

That is convenient for a lab. In a real cloud the platform team works with users of its own instead of oneadmin. Chapter 3.1 shows how users and groups work in OpenNebula.

No passwords in Git

The password of oneadmin is stored in plain text in ~/cc-lab/oneadmin.pass, in the inventory and in ~/.one/one_auth. These files stay on the front-end. Never copy them into your hand-in repo, not even as proof.

Checking

Section titled “Checking”

onehost list shows whether OpenNebula runs and both nodes are ready. The column STAT has to show on for both nodes. OneDeploy registers the nodes with their IP addresses as names.

This output proves requirement 2 of milestone 1. On the client, take a picture of the terminal with Kali's screenshot tool, showing the prompt of your front-end and onehost list with both nodes on. Save it in your home folder as 2-install.png, a name that starts with the number of the requirement. Then open a second tab in the terminal of the client and copy the picture into the folder m1/ of your hand-in repo on the front-end. For the code mmuster that looks like this:

On the front-end you upload it later together with the report of the check install, with git add, git commit and git push as in chapter 0.5.

systemctl and ss show which services run on the front-end and which ports they listen on.

Open the web interface in the browser of the client, which is the Kali VM on smartlearn or your PC if you run your own hypervisor. It listens on port 2616 of your front-end at its new address from chapter 0.3, so for the code mmuster at http://192.168.210.137:2616/. Log in as oneadmin with the password from ~/cc-lab/oneadmin.pass.

After you log in, Sunstone shows its dashboard.

The check of this chapter covers the service, the version, both hosts and the web interface.

Exercise Warm-up

Set up OneDeploy, create the inventory and run the playbook motd.yml twice. Compare the two PLAY RECAP sections and explain why the handler does not run the second time.

Solution

The first run reports changed=2 on both nodes because htop was installed and /etc/motd was written. If htop is already there, as on smartlearn, it shows changed=1. The second run reports changed=0. Since the task "Write the greeting" changed nothing, it does not notify the handler, and the handler does not run.

Exercise Lab

Install OpenNebula 7.4 with OneDeploy, set up the CLI for your user and check the hosts with onehost list. Capture the output in the screenshot 2-install.png and log in to the web interface. Finally upload the report of the check install and the screenshot to your hand-in repo.

Solution

The check ends with "8 of 8 base checks passed". onehost list shows both nodes with on in the column STAT. If it shows err instead, onehost show with the host's name explains why in the section MONITORING INFORMATION, often a missing SSH connection from the front-end to the node. Your hand-in repo then holds reports/install-<time>.txt and m1/2-install.png.

Exercise Deep dive

Match every port that sudo ss -ltnp shows on your front-end to a service from the table. Which ports are reachable only locally, and why does that make sense for the database?

Solution

MariaDB on 3306, OneGate on 5030 and the hook manager on 2101 and 2102 listen only locally, on 127.0.0.1. The database is needed only by oned on the same machine. If it were reachable on the network, anyone with its password could read or change all data of the cloud, bypassing the OpenNebula API. SSH on port 22 and the local DNS cache systemd-resolved on port 53 of 127.0.0.53 and 127.0.0.54 belong to Ubuntu, so the table leaves them out.
