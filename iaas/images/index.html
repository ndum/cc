Images, Vorlagen und Kontext

Auftrag

«Die Praxis Rosenweg möchte eine erste Testmaschine», schreibt Simone Wyss. «Ubuntu, klein, im internen Netz und ohne dass jemand von uns sie von Hand einrichten muss. Geht das in ein paar Minuten?»

Lernziele

Nach diesem Kapitel kannst du:

  • Datastores, Images und Vorlagen unterscheiden
  • Ein Image aus dem Marketplace in deine Cloud holen
  • Die Formate raw und qcow2 sowie persistente und nicht persistente Images unterscheiden
  • Eine Vorlage für VMs lesen und anpassen
  • Erklären, wie die Kontextualisierung eine VM beim ersten Start einrichtet
  • Die Kontextualisierung von OpenNebula mit cloud-init vergleichen
  • Eine VM starten, dich per SSH anmelden und den Check dieses Teils bestehen

Datastores und Images

Abschnitt betitelt „Datastores und Images“

Ein Image ist eine Disk, aus der VMs starten, etwa ein vorbereitetes Ubuntu. Images speichert OpenNebula in Datastores. OneDeploy hat drei davon angelegt. In default liegen die Images, in system die Disks laufender VMs und in files kleinere Dateien wie Skripte. Startet eine VM, kopiert der Transfertreiber ssh ihr Image in den Datastore system des Knotens. Die VM arbeitet auf dieser Kopie, das Image im Datastore bleibt unverändert.

Sunstone zeigt die drei Datastores unter «Storage › Datastores».

Fertige Images liefert der Marketplace von OpenNebula. Mit onemarketapp export holst du ein Image in deinen Datastore. OpenNebula legt dazu eine einfache Vorlage an, die wie das Image ubuntu-26.04 heisst. Der Kurs nutzt sie nicht, sondern legt im Abschnitt «Vorlagen» eine eigene Vorlage ubuntu an.

Das Image ist bereit, sobald oneimage list in der Spalte STAT den Wert rdy zeigt. Auf smartlearn dauerte das rund 30 Sekunden. Die übrigen Befehle von onemarketapp beschreibt die Anleitung zum Marketplace von OpenNebula 7.4.

Formate von Images

Abschnitt betitelt „Formate von Images“

Ein Image im Format raw enthält die Disk Byte für Byte, so wie sie auf einer echten Festplatte läge. Das Format ist einfach, schnell und lässt sich mit jedem Werkzeug lesen. Eine Disk von 30 GB belegt als raw-Datei 30 GB, ausser das Dateisystem unterstützt Sparse Files und reserviert nur die beschriebenen Bereiche, wie die Dokumentation von QEMU erklärt.

Der Name qcow2 steht für QEMU Copy On Write in der Version 2. Die Datei wächst nur mit den tatsächlich beschriebenen Blöcken und kann Snapshots enthalten. Ausserdem kann eine qcow2-Datei auf ein Backing File verweisen, ein anderes Image, aus dem sie nur liest. Braucht die VM einen Block, den die eigene Datei nicht enthält, kommt er aus dem Backing File. Schreibt sie einen Block, landet er in der eigenen Datei. Das Backing File bleibt dabei unverändert, wie die Spezifikation von qcow2 beschreibt. Viele VMs können so ein gemeinsames Grundimage nutzen, jede speichert nur ihre eigenen Änderungen. Auf Datastores mit gemeinsamem Speicher legt OpenNebula neue Disks auf diese Weise an, mit dem Image als Backing File, wie die Dokumentation zu NFS-Datastores zeigt.

Dein Lab nutzt qcow2. oneimage show ubuntu-26.04 zeigt FORMAT : qcow2 und eine Grösse von 3,5 GB, so gross ist die Disk für die VM. Die Datei unter SOURCE belegt im Datastore aber nur rund 450 MB, wie qemu-img info auf dieser Datei zeigt. Weil der Transfertreiber ssh das Image auf den Knoten kopiert, hat die Disk einer VM im Lab kein Backing File. Sie ist eine eigenständige Kopie. Das Kopieren kostet beim Start etwas Zeit, dafür läuft die VM ohne Zugriff auf den Datastore des Front-ends.

Persistente Images

Abschnitt betitelt „Persistente Images“

Ein Image ist in OpenNebula entweder persistent oder nicht persistent. Ein nicht persistentes Image dient als Vorlage für Disks. Beliebig viele VMs können es gleichzeitig nutzen, jede auf ihrer eigenen Kopie. Was eine VM auf ihre Disk schreibt, ist nach dem Beenden der VM weg. Ein persistentes Image behält die Änderungen über das Ende der VM hinaus, darf aber nur von einer einzigen VM gleichzeitig genutzt werden, wie die Dokumentation zu Images festhält. Mit oneimage persistent und oneimage nonpersistent wechselst du die Art.

Das Image ubuntu-26.04 ist nicht persistent, oneimage show zeigt PERSISTENT : No. Für Systemdisks ist das richtig, denn jede VM soll aus demselben Stand starten. Wie viele VMs das Image gerade nutzen, zeigt die Spalte RVMS von oneimage list. Daten, die bleiben müssen, etwa die einer Datenbank, gehören auf eine zweite Disk aus einem persistenten Image. Willst du den Stand einer Disk als neues Image sichern, kopiert onevm disk-saveas sie in den Datastore.

Vorlagen

Abschnitt betitelt „Vorlagen“

Eine Vorlage beschreibt eine VM. Aus derselben Vorlage startest du beliebig viele VMs. Der Kurs liefert die Vorlage ubuntu für kleine VMs im internen Netz.

CPU ist der Anteil eines physischen Kerns, den der Scheduler für die VM reserviert. VCPU ist die Anzahl CPUs, die die VM sieht. Mit CPU = "0.5" und VCPU = "1" passen doppelt so viele VMs auf einen Knoten, wie er Kerne hat, solange nicht alle gleichzeitig voll rechnen. CPU_MODEL mit host-passthrough zeigt der VM die echte CPU, wie Kapitel 1.3 erklärt. DISK nennt das Image, NIC das Netz. Den Block CONTEXT erklärt der nächste Abschnitt.

Wie du Vorlagen anlegst, änderst und mit anderen teilst, zeigt die Anleitung zu VM-Vorlagen.

Kontextualisierung

Abschnitt betitelt „Kontextualisierung“

Ein Image ist für alle VMs gleich, jede VM braucht aber ihre eigene Adresse, ihren Namen und die Schlüssel ihrer Benutzer. Diese Angaben gibt OpenNebula der VM beim Start mit. Es hängt sie als kleines virtuelles CD-Laufwerk an die VM. Das Paket one-context im Image liest sie beim ersten Start und richtet die VM danach ein. Dieses Prinzip heisst Kontextualisierung.

AngabeWirkung in der VM
NETWORK = "YES"Adresse, Gateway, DNS und MTU aus dem Netz cc-net
SSH_PUBLIC_KEYder öffentliche Schlüssel in authorized_keys von root
SET_HOSTNAMEder Hostname, hier der Name der VM
START_SCRIPTein Skript, das beim Start läuft, in Teil 4 für k3s

$USER[SSH_PUBLIC_KEY] übernimmt den Schlüssel vom Benutzer, der die VM startet. Wie du ihn bei oneadmin hinterlegst, zeigt der Abschnitt «Deine erste VM».

Kontextualisierung und cloud-init

Abschnitt betitelt „Kontextualisierung und cloud-init“

OpenNebula schreibt die Werte aus CONTEXT in eine Datei context.sh mit Zeilen der Form NAME='Wert'. Diese Datei legt es auf ein ISO-Abbild, das die VM als CD-Laufwerk sieht, wie die Referenz der VM-Vorlage beschreibt. Im Lab liegt dieses Abbild auf dem Knoten neben der Disk im Verzeichnis der VM, als disk.1 mit der Bezeichnung CONTEXT. Die Kontextualisierungspakete von OpenNebula hängen das Laufwerk beim Start ein, lesen die Variablen und richten danach Netz, Hostname, Schlüssel und Skripte ein. Die Images im Marketplace bringen diese Pakete schon mit.

In öffentlichen Clouds übernimmt meist cloud-init diese Aufgabe. Auch cloud-init richtet eine generische VM beim ersten Start mit den Daten ihrer Instanz ein. Es holt diese Daten aus einer Datenquelle, je nach Cloud aus einem Metadatendienst im Netz oder von einer angehängten Disk. Die Einrichtung selbst kommt meist als YAML-Datei im Format #cloud-config. Für OpenNebula hat cloud-init eine eigene Datenquelle, die dasselbe CD-Laufwerk mit context.sh liest. Ein Image, das für cloud-init gebaut ist, lässt sich also auch in OpenNebula einrichten. Der Unterschied liegt vor allem in der Form der Angaben. OpenNebula arbeitet mit einfachen Variablen, cloud-init mit einer Konfiguration aus Modulen für Pakete, Dateien, Benutzer und Befehle.

Deine erste VM

Abschnitt betitelt „Deine erste VM“

Damit du dich vom Front-end aus an der VM anmelden kannst, legst du zuerst den Schlüssel des Front-ends bei oneadmin ab.

Den Schlüssel übernimmt eine VM, wenn sie entsteht. Hast du web-1 schon vorher gestartet, fragt SSH nach einem Passwort. Beende die VM dann mit onevm terminate web-1 und lege sie mit dem Block unten neu an.

Danach startest du die erste VM aus der Vorlage ubuntu und meldest dich vom Front-end aus per SSH an. Im Lab des Kurses lief sie meist nach wenigen Sekunden und SSH war nach 10 bis 30 Sekunden bereit. Auf smartlearn lief web-1 nach rund 40 Sekunden.

Was die Kontextualisierung eingerichtet hat, siehst du in der VM. hostname zeigt den Namen, ip -br addr die Adresse und ip link show eth0 die MTU. Mit curl -I https://ubuntu.com prüfst du, ob die VM über das Gateway ins Internet kommt. Diese Anmeldung belegt Anforderung 3 von Meilenstein 1. Halte sie mit der Ausgabe von hostname, ip -br addr und curl -I https://ubuntu.com in einem Screenshot fest. Speichere ihn als 3-iaas.png und kopiere ihn wie in Kapitel 2.2 in den Ordner m1/ deines Abgabe-Repos.

Sunstone zeigt den Bildschirm der VM im Browser des Clients. Dazu klickst du unter «Instances › VMs» auf die VM, öffnest oben rechts das Menü mit den drei Punkten und wählst «Console» und dann «VNC». Weitere Befehle für laufende VMs und die Wege zu ihrer Konsole findest du in der Anleitung zu VM-Instanzen.

Der Check dieses Teils prüft das Netz, die Vorlage, eine laufende VM, die Anmeldung per SSH, ihren Hostnamen und den Zugang zum Internet.

Aufgabe Lab

Hole das Image, lege die Vorlage an und hinterlege den Schlüssel des Front-ends bei oneadmin. Starte danach die VM web-1 und halte die Anmeldung im Screenshot 3-iaas.png fest. Lade den Bericht des Checks iaas und den Screenshot in dein Abgabe-Repo.

Lösung

Der Check endet mit «11 von 11 Prüfungen der Basis erfüllt». In der VM zeigt hostname den Namen web-1, ip -br addr eine Adresse aus deinem internen Netz und ip link show eth0 die MTU 1450. Im Abgabe-Repo liegen danach reports/iaas-<zeit>.txt und m1/3-iaas.png.

Aufgabe Vorlage anpassen

Die Treuhand Aaregg braucht am Monatsende eine grössere VM mit zwei CPUs und 2 GB Arbeitsspeicher. Lege eine Kopie der Vorlage unter dem Namen ubuntu-medium an und starte daraus eine VM. Wie viele solcher VMs passen nach onehost list auf einen Knoten?

Lösung

onetemplate clone kopiert die Vorlage. Die neuen Werte schreibst du in eine Datei, die onetemplate update mit --append übernimmt. So ersetzt OpenNebula nur die Werte aus der Datei, alles andere bleibt. Ein Editor geht dabei nicht auf.

Ein Knoten mit rund 7,2 GB Arbeitsspeicher und vier Kernen trägt drei solcher VMs. Die Grenze setzt der Arbeitsspeicher, die CPU reichte für vier. Brauchst du medium-1 nicht mehr, beendest du sie mit onevm terminate medium-1.

Aufgabe Persistente Daten

Die Praxis Rosenweg will in einer VM eine kleine Datenbank betreiben. Die Daten sollen erhalten bleiben, auch wenn die VM beendet und neu angelegt wird. Wie richtest du die Disks ein und was spricht dagegen, einfach das Image ubuntu-26.04 persistent zu machen?

Lösung

Die Systemdisk kommt weiterhin aus dem nicht persistenten Image ubuntu-26.04. Für die Daten legst du ein leeres persistentes Image an, etwa mit oneimage create -d default --name praxis-db --type DATABLOCK --size 2048 --persistent. Dieses Image hängst du als zweite Disk an die VM. Wird die VM beendet, bleiben die Daten im Image. Eine neue VM kann es wieder einbinden. Wäre ubuntu-26.04 persistent, dürfte es nur noch eine VM nutzen. Alle weiteren VMs aus der Vorlage könnten dann nicht mehr starten. Zudem landete jede Änderung an dieser Systemdisk im gemeinsamen Grundimage.
