Glossary

The glossary explains the terms of the course briefly and points to the chapter that introduces them. Many cloud terms stay in English on the German pages as well, such as front-end, deployment or snapshot, so you recognize them in documentation, error messages and tools.

TermMeaningChapter
3-2-1 ruleKeep three copies of important data on two different media, one of them offsite.6.2
AlertmanagerReceives firing alerts from Prometheus, groups similar ones, suppresses repeats and forwards them to receivers such as a webhook.5.3
AlloyThe agent that reads the logs of the pods on each node and sends them to Loki.5.2
AnsibleA tool that brings servers into a described target state over SSH. A second run changes only what is not yet right.2.2
ApplicationAn Argo CD object that defines which folder of which repo belongs in which namespace.4.4
ApplicationSetGenerates Applications from a pattern. In the course it creates one for each folder under members.4.5
Argo CDA set of controllers in the cluster that reads manifests from Git, compares them with the cluster and brings the cluster in line with Git.4.4
Burn rateHow fast a service uses up its error budget. At a burn rate of 1, the budget runs out exactly at the end of the period.5.3
ChargebackUsage is charged to the budget of the unit that caused it.3.3
CheckA course script that tests the state of your lab and writes a report with a hash. Together with the screenshots, the reports of the checks prove the base of a milestone.0.5
ClientThe VM you work from on smartlearn, a Kali Linux desktop with a browser for the web interfaces and a terminal for SSH to the servers. With your own hypervisor, your PC takes this role.0.2
ContainerA process with its own view of the file system, network and processes. It shares the kernel with the host and brings only its application.1.3
ContextualizationOpenNebula hands a VM its address, name, keys and scripts at boot, and the one-context package sets the VM up with them.2.4
Control planeThe part of Kubernetes that runs the cluster, with the API server, scheduler, controllers and database. In k3s it runs on the server.4.3
DatastoreA storage location in OpenNebula. default holds the images, system the disks of running VMs, files smaller files, and from chapter 6.2 on backups the VM backups.2.4
DeploymentKeeps a number of identical pods running and replaces them during an update.4.3
DriftA difference between the actual state and the code, for example after a manual change. tofu plan shows it.4.1
ElasticityResources grow with the load and shrink again, following rules and without manual work.3.5
Error budgetThe share of failures an SLO allows. For the web shop that is 0.5% of requests over seven days.5.3
etcdA distributed database for the state of a cluster. In part 6 it replaces SQLite so k3s can write snapshots.6.2
ExporterA program that offers the metrics of a system in the Prometheus format, such as node_exporter on port 9100.5.1
Front-endThe VM on which OpenNebula manages the cloud, with the service oned, the scheduler and the web interface. In the course it is also the gateway of the internal network.0.2
Full costAll the costs of a service, labor and other items as well as hardware and power. On a small platform, labor is the largest share.6.4
GatewayThe machine through which the VMs of a network reach other networks. In the course the front-end forwards the traffic of the internal network to the internet with NAT.0.2
GiteaA lightweight Git server with a web interface and pull requests. In the course it runs on the front-end and holds the platform repo.4.4
GitOpsThe desired state is versioned in Git, and an agent in the cluster pulls it and keeps reconciling. Changes therefore go through Git.4.4
GrafanaShows queries against Prometheus and Loki as dashboards.5.1
GroupBrings together the users of a tenant in OpenNebula. A group admin manages the people of their member.3.1
HardeningSwitching off or shielding everything that is not needed. In the course that means SSH with keys only, a firewall and automatic updates.6.1
HashA short checksum that changes as soon as the content changes. The check report ends with the hash of its content.0.5
HelmInstalls packages called charts in Kubernetes, with values you adjust.4.2
HorizontalPodAutoscalerAdjusts the number of pods of a deployment to a metric, usually CPU as a percentage of the request. HPA for short.5.4
HypervisorSplits a physical machine into several virtual machines, each with its own CPUs, memory and disks.1.3
IaaSInfrastructure as a service. The provider supplies VMs, networks and storage, and the users run the operating system and the application.1.2
ImageA disk that VMs boot from, such as a prepared Ubuntu. It lives in a datastore.2.4
Infrastructure as codeInfrastructure is described in files, versioned and created by a tool instead of by hand.4.1
InventoryThe file in which Ansible finds the servers and their groups, along with values for all of them or for single ones.2.2
k3sA lightweight Kubernetes distribution in a single program. A server contains the control plane, an agent only runs pods.4.3
KustomizeBuilds the objects for each member from a template and small adjustments without copying the template.4.5
KVMThe hypervisor in the Linux kernel. It uses the virtualization features of the CPU and runs the VMs on the nodes.0.2
Language modelA model that generates text token by token. It writes likely text and does not check whether it is true.5.5
Least privilegeEvery identity gets only the smallest set of rights it needs for its job, such as read-only rights for Prometheus in the course.6.1
LimitRangeSets defaults and upper limits for the requests and limits of each container in a namespace.4.5
LogQLThe query language of Loki. A query first selects streams by labels and then filters the text.5.2
LokiCollects logs centrally and keeps them after a pod is gone. It indexes only a few labels, not the text.5.2
NamespaceA separate area in the Kubernetes cluster. In the course every member gets its own, with a quota and rules.4.3
NATNetwork address translation replaces the source address of packets so that machines on an internal network reach the internet through a single address.0.2
Nested virtualizationA VM passes the virtualization features of the CPU on to its own operating system, so VMs can run inside it.0.2
netplanSets up the network of an Ubuntu server from YAML files in /etc/netplan/. In the course it fixes the addresses of the three servers.0.3
NetworkPolicyDefines who may reach a pod over the cluster network. Without a policy, every pod reaches every other.4.5
nftablesThe packet filter of Linux. In the course it holds the NAT of the gateway and the firewall of the front-end, each in a table of its own.6.1
NodeA VM on which OpenNebula runs the virtual machines of the members. The course has two nodes with KVM.0.2
OllamaLoads open language models and serves them through an HTTP interface. In the advanced tasks of part 5 it can provide the local language model of the platform.5.5
OneDeployThe collection of Ansible playbooks the OpenNebula project uses to install a cloud from a front-end and nodes.2.2
OneFlowManages services made of several VMs in roles and adjusts the number of VMs by rules.3.5
OpenNebulaA free platform for private clouds. It manages nodes, networks, storage and virtual machines and assigns them to tenants.2.2
OpenTofuAn infrastructure-as-code tool and a free fork of Terraform. In the course it creates the k3s VMs in OpenNebula.4.2
PaaSPlatform as a service. The provider also runs the operating system and runtime, and the users bring only their application.1.2
Personal parametersThe values of your lab that come from your personal code, such as host names, the internal network and the VXLAN identifier. They live in /etc/cc-lab.env.0.3
PlaybookA file that describes which steps Ansible runs on which servers.2.2
PodThe smallest unit in Kubernetes, one or more containers that run together on a node and share an address.4.3
Pod Security AdmissionChecks pods against a security profile set by a label on the namespace. The profile restricted rejects pods that run as root, for example.6.1
PostmortemA report after an incident with its course, impact, contributing causes and measures, written without looking for someone to blame.6.3
Private cloudA cloud for a single organization. When several organizations with shared requirements use one cloud together, as at Wolkenwerk Bern, it is called a community cloud.1.2
PrometheusScrapes metrics at fixed intervals and stores them as time series, each a name with labels and timestamped values.5.1
PromQLThe query language of Prometheus, for rates, sums and percentiles over time series.5.1
Protection needsHow strongly data and services need protecting for confidentiality, integrity and availability, measured by the damage a loss would cause.1.4
ProviderTranslates the blocks in OpenTofu code into calls to an API, such as the OpenNebula API on port 2633.4.2
Pull requestA request in Gitea to merge a branch into main. Others review the change before it takes effect.4.5
QuotaAn upper limit on the resources a group or user may take.3.2
RBACRole-based access control. Kubernetes allows a request only what a Role or ClusterRole grants the sender through a binding.6.1
Recording ruleA rule that Prometheus evaluates regularly and stores as a new time series, so alerts and dashboards can read it quickly.5.3
ResourceQuotaLimits the CPU, memory and objects that all pods of a namespace may request together.4.5
Right-sizingAdjusting reserved resources to the measured use.6.4
RPORecovery point objective. The point in time to which data must be recovered after an outage. It says how much data loss is acceptable.6.2
RTORecovery time objective. The longest time a service may be down before the damage becomes unacceptable.6.2
RunbookInstructions for a recurring incident with its symptoms, first checks and measures.6.3
SaaSSoftware as a service. Users get a finished application and manage only their data and access rights.1.2
Sealed SecretsEncrypts a Secret with the public key of a controller into a SealedSecret that may go into Git. Only the controller can decrypt it.6.1
Self-healArgo CD reverts whatever someone changes in the cluster by hand, so the cluster matches Git again.4.4
Self-serviceA member takes resources whenever it needs them, within the limits the platform team sets.3.4
ShowbackShows each unit what it used, without any money changing hands. OpenNebula calculates it from prices in the template.3.3
SLAService level agreement. An agreement with the member on the quality of a service, with consequences if it is missed.6.3
SLIService level indicator. A measurement of how well a service works from the customer's view, usually as the share of good events.5.3
SLOService level objective. The internal target for an SLI over a period. For the web shop it is 99.5% of requests without server errors over seven days.5.3
SnapshotA saved state at one point in time, in smartlearn of a whole VM, in k3s of the cluster database. With an etcd snapshot and the server's token, the cluster can be reset to that state.0.4, 6.2
SSH keyA pair of a private and a public key that lets you log in to a server without a password. After the hardening in chapter 6.1, the front-end accepts keys only.0.5
StateThe file in which OpenTofu records which object in OpenNebula belongs to which block in the code. It holds secret values and stays out of Git.4.1
SunstoneThe OpenNebula web interface on port 2616 of the front-end, for the platform team and the members.2.1
TemplateDescribes a VM in OpenNebula that you can start as many times as you like, such as ubuntu in the course.2.4
TenantAn organization that shares a cloud with others and sees only its own resources.3.1
TLSTransport Layer Security. Encrypts a connection, makes changes in transit detectable and identifies the server with a certificate.6.1
TriageThe first assessment of an alert. In the advanced tasks you build a service that uses the local model to propose a cause and an action from a fixed list, and a person approves it.5.5
VDCVirtual data center. A slice of the infrastructure that OpenNebula assigns to one or more groups.3.1
VXLANA way to carry a network for VMs inside UDP packets across an existing network. In the course it connects the VMs of your cloud through the front-end and the nodes.2.3
