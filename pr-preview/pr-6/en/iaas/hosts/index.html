Operating hosts

Assignment

"Next week node 1 gets more memory," Simone Wyss writes. "The practice must not notice anything. And what actually happens when a node simply fails?"

Learning goals

After this chapter you can:

  • Read and change the states of a host
  • Tell real from allocated capacity and explain overcommitment
  • Describe the rules the scheduler uses to pick a node and read the states of a VM
  • Move VMs to another node with and without interruption
  • Empty a node for maintenance and put it back into service
  • Describe what happens to its VMs when a node fails

States of a host

Section titled “States of a host”

onehost list shows the state of every node in the column STAT.

StateMeaningCommand
onmonitored and ready for new VMsonehost enable
dsblmonitored, running VMs stay, no new VMs are addedonehost disable
offno longer monitored, for nodes that are switched offonehost offline
errmonitoring reports an error, often a missing SSH connection

Under "Infrastructure › Hosts", Sunstone shows the states with their full names, such as "Monitored" for on and "Disabled" for dsbl.

Capacity and overcommitment

Section titled “Capacity and overcommitment”

onehost show lists two values for memory and CPU. USED (ALLOCATED) is what the templates of the running VMs reserve. USED (REAL) is what the node actually uses, its VMs and its own system together. Three VMs from the template ubuntu reserve 3 GB but use a little under 2 GB when idle. In the lab the system of a node adds about 0.6 GB. OpenNebula counts CPU in hundredths of a core, so a node with four cores has 400. A VM with CPU = "0.5" reserves 50 of them.

The scheduler plans with the reserved capacity. Once a node is fully reserved, no further VM starts there, even if its real usage would leave room. With the values RESERVED_CPU and RESERVED_MEM on the host, the platform team can adjust the capacity. A positive value keeps a reserve free. A negative value allows overcommitment, which means that more is reserved on the node than it has. Overcommitment lowers the cost because VMs rarely all work at full load at the same time. If they do all work at once, all of them slow down. Overcommitting memory is riskier than overcommitting CPU, because VMs crash when memory runs out. Missing CPU time only slows them down. The guide to overcommitment of OpenNebula 7.4 shows how to write RESERVED_CPU and RESERVED_MEM, as absolute values or in percent.

Placement by the scheduler

Section titled “Placement by the scheduler”

A new VM waits until the scheduler assigns it a node. By default OpenNebula 7.4 uses the Rank Scheduler for this, and it works in two steps. First it filters. Every node that fails the VM's SCHED_REQUIREMENTS expression or lacks free CPU or memory, measured against the reserved capacity, drops out. Datastores and networks go through the same check. Then it sorts the remaining nodes by the expression SCHED_RANK and takes the one with the highest value. You can set both expressions in a template, for example to start a VM only on nodes with a certain property. Without SCHED_RANK the installation's policy applies. The documentation names four policies.

PolicyRankEffect
PackingRUNNING_VMSfills nodes that already run VMs first and leaves others empty
Striping- RUNNING_VMSspreads VMs across as many nodes as possible
Load-awareFREE_CPUprefers the nodes whose CPU currently has the lowest load
FixedPRIORITYfollows a priority the platform team sets on the host or cluster

In the lab, /etc/one/schedulers/rank.conf contains the entry DEFAULT_SCHED with POLICY = 1, which is striping, unchanged from the file the OpenNebula package ships. That is why your VMs spread across both nodes. Packing needs fewer nodes, so the rest can be switched off. Striping keeps headroom on every node, and a failure hits fewer VMs. Besides the Rank Scheduler, OpenNebula 7.4 includes the Distributed Resource Scheduler. It takes the actual load of the nodes into account and proposes migrations, which the platform team either reviews or lets run automatically.

In Sunstone the "Host" column of the list under "Instances › VMs" shows where each VM ended up.

Life cycle of a VM

Section titled “Life cycle of a VM”

onevm list shows the state of every VM in short form in the column STAT. The state reference lists a great many of them, and in daily work you will mostly meet the following ones.

StateMeaningTrigger
pendwaiting for the scheduler to pick a nodeonetemplate instantiate, onevm resume from unde
prolOpenNebula copies the disks to the nodenode chosen
bootOpenNebula waits for the hypervisor to create the VMcopying finished
runnthe VM is running, including its own boot and shutdownstarted by the hypervisor
poffswitched off, the disks stay on the nodeonevm poweroff
undeswitched off, the disks are back in the system datastore of the front-endonevm undeploy
faila step such as copying or booting failederror in prol, boot or during a migration
unknmonitoring can no longer reach the VMnode failure
doneterminated, onevm list no longer shows the VMonevm terminate

The difference between poff and unde matters for capacity. A powered-off VM keeps its place on the node, while a VM in unde frees it and goes through the scheduler and prol again at its next start. onevm resume starts the VM again from both states. When a VM ends up in fail, its log in /var/log/one/<id>.log shows the cause, and onevm recover brings it back afterwards.

Migration

Section titled “Migration”

onevm migrate moves a VM to another node. Without further options OpenNebula pauses the VM briefly, copies its memory and disk and lets it continue on the target. With --live the VM keeps running during the migration. Only the last part of its memory follows at the end, in a very short moment. In the lab, migrating a small VM took 7 seconds without the option and 10 seconds with --live. The guide to VM instances explains both kinds of migration.

Maintenance of a node

Section titled “Maintenance of a node”

For maintenance you empty a node and then put it back into service. onehost flush disables the node and marks its VMs for rescheduling, after which the scheduler moves them to the other nodes. In onevm list these VMs briefly carry an asterisk in front of their names. In the lab three VMs had moved after about 10 seconds.

After the maintenance you start the node again and release it with onehost enable. New VMs then land on both nodes again. The moved VMs stay where they are until you bring them back yourself. The guide to hosts covers onehost flush and the commands for the states of a host.

Maintenance only works if the remaining nodes have enough capacity for all VMs. With two nodes, each one must be able to carry all VMs alone. Whoever plans such a reserve keeps it free for maintenance and failures and includes it in the cost.

Screenshot of the maintenance

No check covers the maintenance with the migration. For requirement 4 of milestone 1 your screenshot is the only proof. Take it right during the exercise "Maintenance" and name the file something like 4-migration.png, because from chapter 4.2 on the Kubernetes cluster takes up the nodes and neither of them can easily be emptied any more.

Failure of a node

Section titled “Failure of a node”

When a node fails, its VMs stop running. After a while onehost list shows the node as err, and onevm list shows its VMs as unkn. In the lab the disks of running VMs sit in the system datastore of the node itself. As long as the node is down, nobody can reach these disks, and the VMs cannot be started on another node.

A cloud that survives failures therefore needs shared storage that all nodes can reach, such as Ceph or an NFS server, and a rule that automatically restarts the VMs of a failed node on another one. OpenNebula offers hooks for that. The lab deliberately lacks both so that it gets by with the front-end and two nodes. In part 6 this gap is part of the availability assessment.

Exercise Maintenance

Start two VMs from the template ubuntu, empty a node one of them runs on, take it offline and put it back into service. Finally move one VM back live. Write down the commands in the right order.

Solution
  1. onetemplate instantiate ubuntu --name web-2 and --name web-3, then onevm list --size host=15 for the nodes, because without the option the column HOST cuts the address
  2. onehost flush <node> and wait until onevm list shows no asterisk anymore
  3. onehost offline <node>
  4. onehost enable <node> after the maintenance
  5. onevm migrate --live web-2 <node>

Exercise Capacity

Gemeinde Hinterbüel wants to know whether two nodes are enough when one is down for maintenance. Use onehost show to work out how many VMs from the template ubuntu fit on a single node, and explain whether overcommitting memory would be a good idea.

Solution

A node with about 7.2 GB and 400 hundredths of CPU carries seven VMs with 1 GB and 50 hundredths each, so memory sets the limit. Spread over both nodes there must therefore be no more than seven if one node alone has to carry all of them. Overcommitting memory would be risky, because VMs crash when memory runs out, and during maintenance all of them run on one node.

Exercise Scheduler policy

Gemeinde Hinterbüel would like to save power at night by switching off nodes that run no VMs. Which scheduler policy fits, where would you set it, and what does the municipality accept in return?

Solution

Packing fits, because it fills the nodes that already run VMs first and leaves the others empty. You set it in /etc/one/schedulers/rank.conf with POLICY = 0 in the entry DEFAULT_SCHED, or for single VMs with SCHED_RANK = "RUNNING_VMS" in the template. In return more VMs share the same node. If it fails, more VMs are affected, and load peaks of those VMs slow each other down. Packing only affects new placements and does not move existing VMs.
