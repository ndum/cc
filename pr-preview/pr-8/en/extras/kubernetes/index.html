Kubernetes basics

Learning goals

After this chapter you can:

  • Explain how pods, ReplicaSets and deployments relate and how a pod differs from a Docker container
  • Show how labels and selectors tie the objects of the web shop together
  • Name the service types and say where the course uses each one
  • Describe how Traefik passes a request through an ingress to the web shop
  • Recognize namespaces, ConfigMaps, Secrets, requests, limits and probes in a manifest and explain the values
  • Work with kubectl get, describe, logs, exec and apply and say what each command shows

This supplement refreshes the Kubernetes objects you meet from part 4 on. It assumes you have built images and started containers with Docker. How the control plane, the scheduler and the controllers work together is the topic of chapter 4.3. This page looks at the objects you read and write in manifests, using the web shop of chapter 4.4 as the example. The links go to the documentation of Kubernetes 1.36, the version k3s installs in the course.

Pods

Section titled “Pods”

docker run starts a container on a single machine. If that machine fails, nothing starts the container somewhere else. Kubernetes spreads containers across several nodes and keeps running what you described. Its smallest unit is the pod, one or more containers that share a network and volumes. Each pod gets an address of its own, in the lab from 10.52.0.0/16, and containers in the same pod reach each other over localhost. Most pods in the course hold exactly one container. The svclb-traefik-… pods in kube-system, which k3s uses to open the Traefik ports on every node, show 2/2 in the READY column instead, two containers in one pod.

Pods are short-lived. When a pod is deleted or its node fails, a controller replaces it with a new pod that has a different name and address. That is why you rarely create pods yourself. Objects that carry a pod template do it for you, in the course mostly deployments. Alloy in chapter 5.2 runs as a DaemonSet with one pod per node, and Prometheus and Loki run as StatefulSets, whose pods keep a fixed name and a volume of their own.

ReplicaSets and deployments

Section titled “ReplicaSets and deployments”

A ReplicaSet keeps a number of identical pods from one template running. A deployment manages ReplicaSets and replaces the pods step by step when the template changes. You only write the deployment, and the cluster creates the ReplicaSet and the pods. The names show the chain, here for two web shop pods in the lab.

The ReplicaSet is called webshop-7d4f56cb9b. The second part is a hash of the pod template, and each pod adds a random suffix. When you change the template, for example the image or a variable, a new ReplicaSet with a new hash appears. During the switch the deployment may start a quarter more pods than desired, and a quarter may be missing. These are the defaults of maxSurge and maxUnavailable, as the deployment documentation describes. Ten old ReplicaSets stay around with zero pods so that kubectl rollout undo can go back.

Labels and selectors

Section titled “Labels and selectors”

Labels are key-value pairs attached to an object, and a selector picks objects by their labels. With a shared label one object can refer to others without knowing their names. In the web shop, the deployment, the pods and the service all carry the label app: webshop.

ObjectFieldEffect
deployment webshopspec.selector.matchLabelsrecognizes its pods by the label
service webshopspec.selectorsends requests to the ready pods with the label
ServiceMonitor webshop from chapter 5.1spec.selector.matchLabelshas Prometheus scrape the service with the label
Alloy from chapter 5.2rule in discovery.relabelcopies the label into Loki, where {app="webshop"} finds the logs

The deployment controller also adds the label pod-template-hash to every pod, so that pods of the old and the new template can be told apart. Selectors either test for equality, such as app=webshop, or for membership in a set, such as app in (webshop, shop). A service only supports equality. On the command line -l selects by label, for example kubectl -n velo get pods -l app=webshop.

Namespaces carry labels too. Kubernetes sets kubernetes.io/metadata.name on each one, and the member NetworkPolicy of chapter 4.5 uses it to recognize kube-system. In chapter 6.1, namespace labels decide which Pod Security profile applies.

Services

Section titled “Services”

A service gives a changing group of pods a fixed name and a fixed virtual address, in the lab from 10.53.0.0/16. Its type decides where it can be reached from.

TypeReachable throughIn the course
ClusterIPthe virtual address, inside the cluster only, the defaultwebshop in velo, kube-dns in kube-system, Loki in monitoring
NodePortalso a port between 30000 and 32767 on every nodeArgo CD on 30080, Prometheus on 30090, Alertmanager on 30093, Grafana on 30300
LoadBalanceralso an address from a load balancer, in k3s ServiceLB on the node addressestraefik in kube-system on ports 80 and 443
ExternalNamea DNS name outside the cluster, with no address of its ownnot used in the course

The types build on each other. A NodePort service also has a cluster address, and a LoadBalancer service also has ports on the nodes. An excerpt of kubectl get services -A right after the cluster was built shows this.

Traefik has a cluster address, the addresses of both k3s VMs as external addresses and two randomly assigned node ports on top. The web shop service accepts requests on port 80 and forwards them to the port named http of its pods, which the deployment defines as container port 8080.

Inside the cluster, CoreDNS resolves webshop.velo.svc.cluster.local to the service address, and within the same namespace webshop is enough.

Ingress with Traefik

Section titled “Ingress with Traefik”

An ingress is an HTTP rule that says which service receives the requests for a host and a path. The rule does nothing on its own. An ingress controller has to carry it out, and k3s v1.36.5+k3s1 ships Traefik 3.7 for that. k3s installs it in kube-system when the server starts, through its built-in Helm controller, and Traefik runs behind the traefik service from the output above, as the k3s documentation describes.

The web shop rule names no host and only the path /, so every request to port 80 of a k3s VM goes to the webshop service. It names no class either. The Traefik chart creates the IngressClass traefik as the default, so Kubernetes fills it in when the ingress is created. Chapter 4.3 follows a request from Traefik to the pod, and chapter 6.1 explains how an ingress with a tls section would encrypt the traffic.

The Kubernetes project now recommends the Gateway API. The Ingress API is frozen and gets no new features. The course stays with ingress, which k3s supports without extra steps.

Namespaces

Section titled “Namespaces”

A namespace is an area of the cluster. Names only have to be unique within a namespace, which is why velo and gemeinde each have a ResourceQuota called member. Quotas, permissions and network rules apply per namespace, so every member gets its own in chapter 4.5.

NamespaceContents in the lab
kube-systemthe parts of k3s such as CoreDNS, Traefik and metrics-server, from part 6 on also the Sealed Secrets controller
argocdArgo CD and its applications
velo, gemeindethe members with quota, LimitRange and NetworkPolicy, the web shop in velo
monitoringPrometheus, Alertmanager, Grafana, Loki and Alloy from part 5 on
defaultwhatever is created without a namespace, such as the test pods of chapter 4.3

Without -n, kubectl works in the default namespace, and -A covers all of them. Nodes, PersistentVolumes, IngressClasses and namespaces themselves belong to no namespace, and kubectl api-resources --namespaced=false lists every kind of that sort.

ConfigMaps and Secrets

Section titled “ConfigMaps and Secrets”

As with Docker, configuration stays out of the image. A pod mounts it as environment variables or as files in a volume. A ConfigMap holds data that is not confidential, at most 1 MiB. A Secret is meant for passwords, tokens and keys. Its values are only Base64 encoded, though, and by default they sit unencrypted in the cluster database. Anyone allowed to create pods in a namespace can read its Secrets. When a ConfigMap changes, a pod sees the new files after a while, but new environment variables only after a restart.

ObjectIn the courseChapter
ConfigMapthe Alloy configuration, the Grafana dashboards with the label grafana_dashboard5.1, 5.2
SecretArgo CD's access to Gitea, the Grafana password4.4, 5.1
SealedSecretthe Grafana password encrypted in Git, which a controller turns into the Secret6.1

The web shop uses neither. Its settings, SHOP_NAME and from part 5 on WORK_MS and FAIL_PERCENT, are written as env straight into the pod template of the deployment. Any change to them creates a new ReplicaSet and with it a rollout, which is how chapter 5.2 injects a fault with FAIL_PERCENT.

Requests and limits

Section titled “Requests and limits”

Each container can set two values for CPU and memory. The request is what the scheduler reserves for it, and the limit is the ceiling. Above its CPU limit the kernel throttles the container, and above its memory limit the kernel may kill it. 50m means five hundredths of a core, and 64Mi means 64 mebibytes. The web shop requests 50m and 64Mi and may use up to 500m and 128Mi, from part 5 on only up to 250m of CPU.

In the member namespaces, a LimitRange sets values for containers that bring none, and a ResourceQuota caps the total, both from chapter 4.5. The HorizontalPodAutoscaler of chapter 5.4 measures CPU as a percentage of the request. Chapter 4.3 explains how the scheduler plans with requests, and the resource management documentation has the rules.

Probes

Section titled “Probes”

The kubelet uses probes to check whether a container is healthy. Docker has the HEALTHCHECK instruction for this, while Kubernetes distinguishes three probes with different consequences.

ProbeQuestionWhen it fails
ReadinessCan the container accept requests?Its address leaves the EndpointSlice of the service, the pod keeps running.
LivenessIs the container still working?The kubelet restarts the container.
StartupHas the container finished starting?The kubelet restarts the container. The other two probes wait until it succeeds.

The web shop checks /healthz for readiness and liveness and has no startup probe. By default the kubelet probes every 10 seconds, waits one second for an answer and counts the probe as failed after three failures in a row. The web shop waits three seconds with timeoutSeconds: 3. Under the load of part 5 a pod answers more slowly, and a failed liveness probe would restart it in the middle of the load test. Readiness also decides when a new pod counts as available during a rollout.

Manifests and the declarative model

Section titled “Manifests and the declarative model”

A manifest describes an object in YAML. apiVersion and kind name its type, metadata holds the name, namespace, labels and annotations, and spec the desired state. The cluster writes status itself and reports there what it actually finds. There are three ways to manage objects.

TechniqueExampleIn the course
Imperative commandskubectl create deployment, kubectl scaleshort tests in chapters 4.3 and 4.5
Imperative object configurationkubectl create -f webshop.yamlnot used
Declarative object configurationkubectl apply -f folder/Argo CD for your whole repo, you yourself mainly at the bootstrap with root.yaml

kubectl apply creates missing objects and changes existing ones until they match the manifest. To do so, kubectl keeps the last applied version in the annotation kubectl.kubernetes.io/last-applied-configuration. If you remove a field from the manifest, apply removes it from the cluster too. Fields that never appear in the manifest stay untouched, even when someone else set them.

Part 5 relies on that rule. The web shop deployment no longer names a number of pods there and leaves the replicas field to the HorizontalPodAutoscaler. In part 4 the manifest still says replicas: 2, which is why Argo CD in chapter 4.4 reverts a kubectl scale right away. kubectl diff shows what an apply would change before you run it. Chapter 4.1 goes deeper into declarative and imperative, and the object management documentation describes all three techniques.

Exercise Lab

Use the commands above to follow a request to the web shop from the ingress to the container. For each step, name the object and the selector or port that links it to the next one. Then explain what happens when a pod fails its readiness probe three times. How would a failing liveness probe differ?

Solution

The ingress webshop has the class traefik and sends every path to the service webshop on the port http. The service selects the pods with app=webshop and forwards port 80 to the container port named http, which is 8080. Its EndpointSlice holds the addresses of the ready pods. The pods belong to the ReplicaSet webshop-<hash>, which selects with app=webshop and pod-template-hash and in turn belongs to the deployment webshop. describe shows both probes as http-get http://:http/healthz with timeout=3s period=10s #success=1 #failure=3.

After three failed readiness probes, Kubernetes removes the pod's address from the EndpointSlice. The pod keeps running but gets no requests until the probe succeeds again. After three failed liveness probes, the kubelet restarts the container. kubectl get pods then counts up RESTARTS, and kubectl logs --previous shows the logs from before the restart.
