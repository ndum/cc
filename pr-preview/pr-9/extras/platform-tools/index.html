Werkzeuge der Plattform

Lernziele

Nach diesem Kapitel kannst du:

  • Für jedes Werkzeug der Plattform sagen, wozu es dient, wie es ins Lab kommt und in welchem Kapitel es vorkommt
  • Den Aufbau von Argo CD, des Monitoring-Stacks und von Sealed Secrets in wenigen Sätzen beschreiben
  • Helm und Kustomize unterscheiden und erklären, wie Argo CD beide nutzt
  • Die Versionen in deinem Plattform-Repo finden und die Dokumentation derselben Version öffnen
  • In deinem Lab mit Befehlen, die nichts ändern, nachsehen, wie jedes Werkzeug läuft

Ab Teil 4 kommen neun Werkzeuge dazu. Die Kapitel führen jedes dort ein, wo es gebraucht wird. Diese Ergänzung sammelt Zweck, Aufbau, Begriffe und Installation an einem Ort. OpenTofu und Gitea fehlen hier, sie stehen ausführlich in den Kapiteln 4.2 und 4.4.

Fast alles kommt über Argo CD in den Cluster. Argo CD holt dein Repo aus Gitea, rendert Charts mit Helm und Ordner mit Kustomize und wendet das Ergebnis an.

Argo CD

Abschnitt betitelt „Argo CD“

Argo CD ist ein Projekt der CNCF und ein Controller für GitOps. Er vergleicht den Soll-Zustand aus Git mit dem Ist-Zustand im Cluster und gleicht Abweichungen an. Im Namespace argocd laufen dafür mehrere Teile, wie die Beschreibung der Architektur zeigt.

TeilAufgabe
API-ServerWeboberfläche und API, im Lab als NodePort 30080
Repository-Serverholt die Repos, rendert die Manifeste mit Helm oder Kustomize und hält sie im Cache
Application Controllervergleicht Soll und Ist, führt den Sync aus und meldet Sync-Status und Health
ApplicationSet-Controllererzeugt Applications nach einem Muster, im Kurs eine pro Ordner unter members
RedisCache für die anderen Teile

Eine Application verbindet eine Quelle in Git mit einem Ziel im Cluster. Der Sync-Status sagt, ob der Cluster Git entspricht (Synced oder OutOfSync), Health, ob die Objekte laufen (Healthy, Progressing oder Degraded). Ein Refresh vergleicht nur, ein Sync wendet an. Prune löscht, was aus Git verschwunden ist, Self-Heal setzt Änderungen von Hand zurück. Liegt in einem Ordner eine Chart.yaml, rendert Argo CD mit Helm, bei einer kustomization.yaml mit Kustomize, sonst nimmt er die Dateien, wie sie sind. Jedes verwaltete Objekt trägt die Annotation argocd.argoproj.io/tracking-id. Die Grundbegriffe stehen in der Dokumentation von Argo CD 3.5.

Das Skript bootstrap-argocd.sh aus Kapitel 4.4 installiert das Chart mit Helm. Seine Werte schalten Dex für die Anmeldung über fremde Konten und den Dienst für Benachrichtigungen aus. Die Oberfläche antwortet ohne TLS. Argo CD fragt Git jede Minute ab statt alle drei Minuten. Danach legt das Skript das Secret mit dem Lese-Token für Gitea an und wendet root.yaml an, alles Weitere entsteht aus Git. Argo CD wendet die Manifeste wie kubectl apply an. Die Application monitoring nutzt ServerSideApply=true, weil die Definitionen des Prometheus Operator für die Annotation eines gewöhnlichen apply zu gross sind. Eigene AppProjects neben default sind Thema der Zusatzaufträge von Kapitel 4.6.

Helm

Abschnitt betitelt „Helm“

Helm ist ein Paketmanager für Kubernetes. Ein Chart ist ein Paket aus Vorlagen für Manifeste, der Datei values.yaml mit Standardwerten und der Datei Chart.yaml mit version und appVersion. Charts liegen in Repositories, die von Argo CD etwa unter https://argoproj.github.io/argo-helm. Ein Release ist ein installiertes Chart im Cluster. Eigene Werte gibst du mit -f werte.yaml oder --set mit. Die Releases speichert Helm als Secrets im Cluster, eine eigene Datenbank braucht es nicht. Die Einführung in Helm beschreibt diese Begriffe für Helm 4.

Auf dem Front-end legt Helm im Kurs genau ein Release an, argocd im Namespace argocd, mit helm upgrade --install aus dem Bootstrap-Skript. Die Charts der Teile 5 und 6 erzeugt Argo CD mit helm template nur als Manifeste und verwaltet diese danach selbst, wie die Dokumentation von Argo CD zu Helm beschreibt. helm list zeigt sie deshalb nicht, ein Rollback geht über git revert. Auch k3s nutzt Helm. Sein eingebauter Helm-Controller installiert Traefik aus Objekten vom Typ HelmChart in kube-system.

Kustomize

Abschnitt betitelt „Kustomize“

Kustomize setzt Manifeste aus gewöhnlichem YAML zusammen, ohne Vorlagensprache. Die Datei kustomization.yaml zählt unter resources die Dateien eines Ordners auf und bindet unter components Komponenten ein. Mit namespace setzt sie den Namespace aller Objekte, mit patches ändert sie einzelne Felder. Ein Patch ist entweder ein JSON-Patch mit Operationen wie op: replace oder ein Strategic-Merge-Patch, ein Stück YAML, das Kustomize mit dem Original zusammenführt. Eine Komponente mit kind: Component ist ein Baustein, den mehrere Ordner einbinden können.

Im Kurs ist templates/member aus Kapitel 4.5 eine solche Komponente mit Namespace, ResourceQuota, LimitRange und NetworkPolicy. members/velo setzt den Namespace velo und ersetzt mit einem JSON-Patch den Wert für requests.cpu. Auch webshop/ ist ein Ordner mit kustomization.yaml. kubectl kustomize zeigt das Ergebnis, ohne etwas anzuwenden. Argo CD bringt im Repository-Server eigene Fassungen von Kustomize und Helm mit. Die Dokumentation von Kubernetes 1.36 und die Referenz der Patches beschreiben alle Felder.

HelmKustomize
AnsatzVorlagen mit Platzhaltern, gefüllt aus Wertenfertiges YAML, verändert durch Patches
PaketChart mit Version in einem RepositoryOrdner in Git
Im Kurs fürSoftware anderer Projekte, etwa Argo CD, Loki und Sealed Secretseigene Manifeste, also Webshop und Mitglieder

Prometheus

Abschnitt betitelt „Prometheus“

Prometheus holt Messwerte in festen Abständen über HTTP bei seinen Zielen ab und speichert sie als Zeitreihen auf der Disk. Abfragen schreibst du in PromQL. Regeln rechnet Prometheus regelmässig aus. Recording Rules speichern ihr Ergebnis als neue Zeitreihe, Alerting Rules schicken auslösende Alerts an Alertmanager. Für Systeme ohne eigenes /metrics gibt es Exporter, etwa den OpenNebula-Exporter auf Port 9925.

Im Lab kommt Prometheus mit dem Chart kube-prometheus-stack aus Kapitel 5.1. Neben Prometheus, Alertmanager und Grafana bringt es drei Teile mit. Der Prometheus Operator 0.94.2 führt eigene Objektarten ein und schreibt daraus die Konfiguration von Prometheus. Der Dienst kube-state-metrics meldet den Zustand der Objekte im Cluster, etwa die bereiten Pods eines Deployments. Der node-exporter läuft als DaemonSet und liefert die Werte jedes Nodes.

ObjektartInhaltIm Kurs
ServiceMonitorwelche Services Prometheus abfragtwebshop in velo, alle 15 Sekunden
ScrapeConfigZiele ausserhalb des Clustersdie Exporter von OpenNebula
PrometheusRuleRecording und Alerting Rulesdas SLO des Webshops aus Kapitel 5.3

Die Werte des Kurses behalten Daten drei Tage auf einem Volume von 5 GiB und öffnen den NodePort 30090. Prometheus liest Monitore und Regeln aus allen Namespaces, auch solche, die nicht aus dem Chart stammen. Die Monitore für etcd, Scheduler, Controller Manager und Proxy sind aus, weil k3s diese Teile in einem einzigen Prozess ausführt. Die Grundlagen von PromQL gelten für Prometheus 3.15, die Objektarten des Operators stehen auf seiner Website.

Alertmanager

Abschnitt betitelt „Alertmanager“

Alertmanager nimmt die Alerts von Prometheus an und entscheidet, wer davon erfährt. Er fasst Alerts mit gleichen Labels zu Gruppen zusammen und verschickt eine Gruppe nur einmal pro Intervall. Mit Inhibition unterdrückt er Meldungen, solange bestimmte andere Alerts schon auslösen. Eine Silence schaltet Alerts für eine gewisse Zeit stumm. Routen weisen Alerts nach ihren Labels einem Empfänger zu, etwa einem Webhook oder einer E-Mail-Adresse. Die Dokumentation von Alertmanager 0.34 erklärt diese Begriffe.

Im Lab läuft Alertmanager aus demselben Chart mit dem NodePort 30093. Die Werte des Kurses gruppieren nach alertname und namespace und schicken alle Alerts an den Empfänger null, der nichts verschickt. Die Alerts erscheinen darum nur in der Oberfläche. Dort steht auch Watchdog, eine Regel des Charts, die immer auslöst und damit zeigt, dass die Kette von Prometheus bis Alertmanager funktioniert. Kapitel 5.3 erklärt die Weiterleitung, einen eigenen Empfänger richtest du in den Zusatzaufträgen von Kapitel 5.5 ein.

Grafana

Abschnitt betitelt „Grafana“

Grafana stellt Abfragen als Dashboards dar. Eine Datenquelle ist die Verbindung zu einem Speicher wie Prometheus oder Loki. Ein Dashboard besteht aus Panels, jedes Panel zeigt eine oder mehrere Abfragen. Unter «Explore» probierst du Abfragen ohne Dashboard aus.

Im Lab gehört Grafana zum Chart kube-prometheus-stack und ist auf NodePort 30300 erreichbar. Die Datenquelle Prometheus richtet das Chart selbst ein, Loki kommt über additionalDataSources aus den Werten dazu. Das Passwort von admin liegt im Secret grafana-admin, ab Kapitel 6.1 aus einem SealedSecret. Ein weiterer Container im Pod, ein sogenannter Sidecar, lädt jede ConfigMap mit dem Label grafana_dashboard als Dashboard, auch das Dashboard des Plattform-Teams aus Kapitel 5.1. Grafana hat im Lab kein Volume. Was du in der Oberfläche änderst, geht beim nächsten Neustart des Pods verloren, Dashboards gehören darum in Git.

Loki

Abschnitt betitelt „Loki“

Loki speichert Logs und indexiert dabei nur die Labels, etwa Namespace und Pod, nicht den Text. Alle Zeilen mit denselben Labels bilden einen Stream. Den Text legt Loki komprimiert in Chunks ab und durchsucht ihn erst bei einer Abfrage in LogQL. Eine Abfrage liefert entweder Zeilen oder macht aus Zeilen eine Metrik, etwa mit count_over_time. Die Übersicht von Loki 3.6 beschreibt den Aufbau, die Seite zu LogQL die Abfragen.

Im Lab läuft Loki im monolithischen Modus, den das Chart SingleBinary nennt. Alle Teile stecken in einem Prozess, die Daten liegen im Dateisystem auf einem Volume von 5 GiB. Nach 72 Stunden löscht der Compactor sie. Die Beschreibung der Betriebsarten empfiehlt diesen Modus für kleine Mengen bis etwa 20 GB am Tag. Eine Anmeldung gibt es nicht, Grafana und Alloy erreichen Loki unter loki.monitoring.svc:3100. Welche Labels in den Index gehören, steht in Kapitel 5.2.

Alloy

Abschnitt betitelt „Alloy“

Alloy von Grafana sammelt Daten wie Metriken und Logs und schickt sie weiter. Seine Konfiguration besteht aus Komponenten. Jede erledigt eine Aufgabe, bekommt Argumente und gibt Exporte weiter, die andere Komponenten verwenden. Daraus entsteht eine Kette.

Im Lab läuft Alloy als DaemonSet mit einem Pod pro Node. Die Kette aus Kapitel 5.2 hat vier Glieder. discovery.kubernetes findet die Pods, discovery.relabel macht daraus die Labels namespace, pod, container und app. loki.source.kubernetes liest die Logs, loki.write schickt sie an Loki. Die Komponente loki.source.kubernetes liest die Logs über die API von Kubernetes und könnte so jeden Pod im Cluster erreichen. Darum sucht discovery.kubernetes in jeder Instanz mit einem Selektor auf spec.nodeName nur die Pods des eigenen Nodes. Den Namen des Nodes bekommt Alloy als Variable NODE_NAME aus seinem eigenen Pod.

Sealed Secrets

Abschnitt betitelt „Sealed Secrets“

Ein Secret in Git wäre für alle lesbar, die das Repo lesen dürfen. Sealed Secrets löst das mit zwei Teilen. Ein Controller im Cluster erzeugt ein Schlüsselpaar. kubeseal auf dem Front-end holt den öffentlichen Schlüssel und verschlüsselt damit ein Secret zu einem SealedSecret, das in Git darf. Nur der Controller kann es mit seinem privaten Schlüssel öffnen. Er legt daraus ein gewöhnliches Secret an, dessen Besitzer das SealedSecret ist. Im Standard strict sind Name und Namespace Teil der Verschlüsselung. Der Controller erneuert seinen Schlüssel alle 30 Tage und behält die alten. Gehen die privaten Schlüssel verloren, öffnet niemand mehr ein SealedSecret, darum sichert Kapitel 6.2 sie auf dem Front-end. Die Beschreibung von Sealed Secrets 0.41.2 erklärt die Varianten.

Im Lab bringt die Application sealed-secrets aus Kapitel 6.1 den Controller nach kube-system. Er heisst dort sealed-secrets-controller, so wie kubeseal ihn sucht. install-kubeseal.sh installiert kubeseal und prüft dabei die Prüfsumme. seal-secrets.sh schreibt das Passwort von Grafana als secrets/grafana-admin.yaml ins Plattform-Repo. Die Application secrets bringt es von dort in den Cluster.

Im Lab

Abschnitt betitelt „Im Lab“

Ab Teil 6 sind alle neun Werkzeuge im Einsatz. Die folgenden Befehle auf dem Front-end lesen nur und ändern nichts.

Helm zeigt nur Releases, die es selbst installiert hat, darunter argocd mit dem Chart argo-cd-10.11.6. grep zeigt für jede Application mit einem Chart dessen Namen und die Version aus Git.

Du siehst je einen Pod für Server, Repository-Server, Application Controller, ApplicationSet-Controller und Redis, dazu alle Applications mit Sync-Status und Health.

Die Ausgaben listen die Objektarten, die Argo CD, der Prometheus Operator und Sealed Secrets im Cluster einführen, etwa applications, servicemonitors und sealedsecrets.

Der erste Befehl zeigt, woher Prometheus Ziele und Regeln bekommt, aus dem Chart und aus deinem Repo. Der zweite listet die Dashboards, die Grafana lädt.

Loki läuft in einem Pod, Alloy in einem Pod pro Node. Das SealedSecret grafana-admin steht mit True in der Spalte SYNCED, sobald der Controller es entschlüsselt hat. Die letzte Zeile nennt neben kubectl die Version von Kustomize.

Aufgabe Lab

Erstelle für dein Lab eine Tabelle der neun Werkzeuge. Trage für jedes ein, wie es ins Lab kam, welche Version läuft, in welchem Namespace oder auf welcher VM es liegt und welche Datei seine Einstellungen festlegt. Erkläre danach, warum helm list -A die Charts aus Teil 5 nicht zeigt. Was geschieht, wenn du in deinem Plattform-Repo die targetRevision von Loki änderst und pushst?

Lösung

Argo CD 3.5.6 kam mit Helm aus dem Chart 10.11.6 und läuft in argocd, seine Werte stehen in platform/argocd/values.yaml im Kursrepo. Helm und kubectl liegen als Pakete auf dem Front-end, helm version und kubectl version --client nennen die Versionen, kubectl auch die von Kustomize. Kustomize hat keine eigene Installation, seine Dateien sind die kustomization.yaml in webshop/, templates/member/ und members/. Prometheus, Alertmanager und Grafana kommen über die Application monitoring mit kube-prometheus-stack 92.17.0 nach monitoring, die Werte stehen in monitoring/kube-prometheus-stack.yaml. Loki und Alloy kommen über apps/loki.yaml, die Werte stehen in monitoring/loki.yaml und monitoring/alloy.yaml. Der Controller von Sealed Secrets kommt über apps/sealed-secrets.yaml nach kube-system, kubeseal liegt in /usr/local/bin auf dem Front-end.

helm list -A zeigt nur Releases, die Helm selbst installiert hat, also argocd und je nach Stand die Releases, mit denen k3s Traefik einrichtet. Argo CD rendert die übrigen Charts mit helm template und wendet die Manifeste selbst an, ein Release entsteht dabei nicht. Nach dem Push erkennt Argo CD die neue targetRevision innert ein bis zwei Minuten, rendert die neue Version des Charts mit deinen Werten und passt die Objekte an. Zurück geht es mit git revert. Vorher lohnt ein Blick in die Hinweise zum Upgrade des Charts, weil neue Versionen manchmal den Aufbau der Werte ändern.
